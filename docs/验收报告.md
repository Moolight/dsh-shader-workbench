### 2.5 编译

| 验收项 | 结论 | 证据 |
|---|---|---|
| 同图导出 GLSL | **通过** | `shader_export` 写 `shader.frag` + `bundle.json`；面板可直接下载生成的 .frag |
| 导出 HLSL / MSL / SPIR-V | **通过（SPIR-V 有一处诚实边界）** | 目标注册表现在有 5 个：`glsl` / `hlsl` / `msl` / `spirv` / `spvasm`。HLSL、MSL 是源码级转译，**在 24 个采样点上与原 GLSL 逐点数值相等**（`cross-compile.test.js`，12 个 pass × 3 个目标，0 失败）。SPIR-V 由自研编码器产出二进制：全部 12 个 pass 都能生成**结构自洽 + 编解码逐字节互逆**的模块。**⚠️ 本机没有 `spirv-val`，所以这份二进制没有经过官方校验器** —— 见第 4 节 |

> 跨平台转译**不依赖任何外部 shader 工具链**。本机 `glslangValidator` / `spirv-cross` /
> `glslc` / `dxc` / `fxc` / `naga` / `tint` / `slangc` 一个都没有，而项目要求零依赖 + 全离线，
> 所以解析器、转译器、SPIR-V 二进制编码器、反汇编器、结构校验器全是手写的。

## 3. 真机验证详情

### 3.1 GLSL 编译（`glsl-compile.test.js`）

用无头 Edge 起**真 WebGL2 上下文**，把每个节点单独成图后编译并链接。

```
[glsl] 渲染器：WebKit / WebKit WebGL
[glsl] 编译探针：50 个，失败 0 个      ← 节点库里的每一个节点
[glsl] 编译探针：3 个，失败 0 个       ← image Pass + BufferA Pass + 默认空白图
```

**这个测试抓到了 6 个只有编译器才能发现的 bug**，全部已修：

| # | Bug | 编译器报错 | 修法 |
|---|---|---|---|
| 1 | 生成的着色器缺 `#version 300 es` | `'out' : storage qualifier supported in GLSL ES 3.00 and above only` | header 第一行补上 |
| 2 | `st_pow` 把 `float` 与 `vec4` 混在一个重载集里 | `function must have the same return type in all of its declarations` | 删掉跨返回类型的重载 |
| 3 | `const` 节点 value 是 vec3、outType 是 float | `dimension mismatch` | 按**输出端口类型**重新序列化值 |
| 4 | `custom` 节点的表达式 `$in.a` 只展开一层 | `'$' : invalid character` | `substitute` 改递归展开 |
| 5 | uniform 声明带初始化器 | `cannot initialize this type of qualifier` | ES 3.00 不允许，声明改为裸的 |
| 6 | vec3 → vec4 提升时 alpha 补 0 | 编译能过，但画面**全透明** | 第 4 位改补 1.0 |

第 6 个特别值得记：它不是编译错误，是**语义错误**，编译器不报，
但会让用户第一次打开就看到一片空白。

### 3.2 GPU 像素回读（`render-gpu.test.js`）

编译通过 ≠ 画得对。这个测试用 `gl.readPixels` 把画布正中心的像素读回来对值。

```
[gpu] 环境 = {"renderer":"WebKit WebGL","floatBuffers":true,"size":{"w":128,"h":128}}
[gpu] iChannel0=red                {"r":255,"g":0,"b":0,"a":255}     ← 绑纯红图
[gpu] iChannel0=unbound            {"r":32,"g":32,"b":32,"a":255}    ← 解绑 → 兜底灰，不是黑
[gpu] iChannel3=red                {"r":255,"g":0,"b":0,"a":255}     ← 红绑在 iChannel3
[gpu] iChannel0=still-unbound      {"r":32,"g":32,"b":32,"a":255}    ← iChannel0 没串台
[gpu] iChannel3=blue               {"r":0,"g":0,"b":255,"a":255}     ← 换源生效（旧纹理已释放）
[gpu] bufferA=green                {"r":0,"g":255,"b":0,"a":255}     ← BufferA → image 多 Pass 反馈
[gpu] mouse-uv                     {"r":64,"g":191,"b":0,"a":255}    ← iMouse
```

最后一行是重点：鼠标移到画布 (32,32)，画布 128×128，所以
`iMouse.zw = [32, 96]`，`uv = [0.25, 0.75]`，
期望像素 `[0.25×255, 0.75×255] = [64, 191]` —— **与实测完全一致**。

这一步把三块之前「只有代码、没有验证」的能力钉死了：
纹理绑定、兜底路径、Buffer 双缓冲的「上一帧」语义。

### 3.3 编辑器真鼠标拖拽（`editor-interaction.test.js`）

用 CDP 的 `Input.dispatchMouseEvent` 走**真输入通道**，
坐标由页面自己用 `portPosition()` / `nodeHeaderPosition()` 现算。

```
[editor] 画布尺寸 = {"w":560,"h":471}
[editor] 端口坐标 = {"out":{"x":488,"y":222},"in":{"x":540,"y":162}}
[editor] hitAtOut = {"world":{"x":248,"y":103},"hit":{"kind":"port","nodeType":"uv","portId":"out","dir":"out","index":0}}
[editor] 连线过程 = [
  {"phase":"afterDown","drag":{"kind":"edge","fromPort":"out"},"edges":0},
  {"phase":"afterMove","drag":{"kind":"edge","fromPort":"out"},"edges":0},
  {"phase":"afterUp","drag":null,"edges":1,"status":"2 节点 / 1 连线 · 缩放 100% · 选中 1"}
]
[editor] 拖前   = uv(0,0)   edges: []
[editor] 拖后   = uv(80,60) edges: []            ← 位移与鼠标位移精确一致
[editor] 连线后 = uv(80,60) edges: [uv.out → output.color]
[editor] 重连后 = uv(80,60) edges: [uv.out → output.color]   ← 仍是 1 条（替换而非叠加）
[editor] 再拖后 = uv(40,30) edges: [uv.out → output.color]
[editor] 事件   = [move-node, connect, connect, move-node]
```

**这个测试抓到了 2 个真 bug**（都是编译过、单测过、模板看不出问题的）：

| # | Bug | 为什么之前没暴露 | 修法 |
|---|---|---|---|
| 1 | **`_canDrop` 读已被清空的 `this.drag`** → 手动拖线**从来没成功过** | `_onPointerUp` 一进来就 `this.drag = null`；内置示例模板走 `_link()` 绕过检查直接连，所以演示看起来一切正常 | 把 drag 当参数显式传进 `_canDrop(hit, drag)` |
| 2 | **`canConnect` 比生成器更严** → `uv`(vec2) → `output`(vec4) 这种最基本的连法被拒 | 生成器 `castExpr` 支持 16 种组合，编辑器只放行 6 种；模板又绕过检查 | 改成 16 种全放行，有损性交给 `conversionKind` 在状态栏提示 |

第 1 个是本项目最值得记的 bug：**没有任何自动化检查能发现它**，
除非真的用鼠标拖一次。这也是「为什么要有交互测试」的最好论据。

### 3.4 面板端到端冒烟（`panel-smoke.test.js`）

真浏览器 + 真 DOM + 真 WebGL2，把工作台整块挂起来，再打开一个真材质。

```

[smoke] 材质 = demo / plasma
[smoke] 图 = 7 节点 / 6 连线

```

（`failures: 1` 是打开材质**之前**那次空图的预期失败——空 Pass 没有输出节点。
工作台对这种情况显示的是灰色提示而不是红错。）

**这个测试抓到的 bug**：

| # | Bug | 表现 | 修法 |
|---|---|---|---|
| 1 | `/module/` 路由只认 `client/` | 面板 import `../../shared/*.js` 全部 404，白屏 | 白名单加 `shared/` 与插件根，并把 `module/` 后的整条路径规范化（URL 层级与磁盘深度对不上） |
| 2 | `Workbench` 漏了再导出 | `mod.Workbench is not a constructor` | `panel/index.js` 补 `export { Workbench }` |
| 3 | `_materialLabel()` 方法根本没写 | 构造函数抛错，面板整个建不起来 | 改成直接建 DOM 节点 |
| 4 | `material.list` 返回 `{materials:[...]}` 被当裸数组用 | 资源树显示 `undefined`、项目不展开 | 取 `.materials` |
| 5 | 空图被当成编译错误 | 一打开就是红框报错 | 区分 `empty-pass`，显示灰色提示 |

## 4. 需要人工复核的项（诚实清单）

自动化能覆盖的都已经覆盖了。**只剩一项必须人眼看**：

| # | 项 | 怎么验 | 为什么自动化验不了 |
|---|---|---|---|
| 1 | **画面的审美是否正确** | 重启 DSH → 点侧栏「Shader 工作台」→ 打开 demo/plasma 或点「插入示例」→ 预览区应出现随时间流动的彩色等离子体 | 自动化能证明「编译通过 + 出帧 + 像素取值正确」，证明不了「好看」 |

原本列在这里的「面板能否打开」「拖拽是否可用」「iChannel/iMouse 是否生效」
现在都已经转为自动化覆盖：

| 项 | 现在由谁覆盖 |
|---|---|
| 面板能否挂载 / 会不会白屏 | `panel-smoke`（真浏览器 + 真 DOM） |
| 拖拽能否移动节点、能否连线 | `editor-interaction`（真 CDP 鼠标事件） |
| iChannel0-3 有没有真的绑上 | `render-gpu`（读像素） |
| iMouse 位置算得对不对 | `render-gpu`（读像素，与公式精确吻合） |
| Buffer 反馈拿的是不是上一帧 | `render-gpu`（读像素 = 绿） |
| GLSL 能不能编译 | `glsl-compile`（50 探针） |
| 1080p 帧率 / 隐藏时空转 | `perf-1080p`（GPU timer query） |
| HTTP API 通不通、路径安全 | `http` / `workspace` |
| 插件会不会让 DSH failed | `plugin-load` |

## 5. 已知限制

| 限制 | 说明 |
|---|---|
| 不能从浏览器拿文件绝对路径 | 导入纹理走「让用户填磁盘路径」的方式（DSH 是本地桌面应用，路径可达）。真正的拖拽上传留待后续 |
| 一个输入端口连多条线 | 图里都保留（`normalizeGraph` 去重后仍可能有多条来源），但生成器只用第一条（`find` 语义）。**编辑器连线时会把同目标的老线替换掉**，所以 UI 上不会积 |
| 撤销重做覆盖 | 快照式撤销栈覆盖节点图改动（含同类合并 + 数量/字节双预算）；但删除/清空 Pass 仍是即时且不可撤销的（`shader_graph_build` 会自动打一份快照兜底） |
| 分组框 / 注释 | 已实现，是画布层装饰件（`passes[].frames`），不参与代码生成、删框不删节点；真正的复用请用 Group 元节点 |
| DDS 不做转码 | 只按普通图片绑槽位，不解析 mipmap / ASTC |
| 面板路径不能跨出 `client/` `/shared/` / 插件根 | 这是 `/module/` 路由的白名单，出于安全考虑 |
| 有损转换只提示不阻止 | `vec4 → vec2` 会静默丢 zw，状态栏给提示但允许连。设计取舍：生成器规则是确定的，用户有权这么接 |
| ComfyUI 未做 | 见第 2.4 节（跨编译 FR-06 已完成，见第 2.5 节） |

### 与需求书的偏离（已确认，需记录）

1. **不引入构建链**：需求书建议 Vite + TypeScript + pnpm workspace，
   本版手写 ESM JavaScript、`node --test`。核心理由是「轻量 + 离线可用」这两条非功能需求。
2. **节点编辑器自研，不用 Rete.js**：需求书建议 Rete.js + React。
   自研的理由是包体与可控性；代价是分组/注释/撤销重做要自己写（本版未写）。
3. **单包而非 Monorepo**：三个包合并为一个包的三个目录。
   零构建链的前提下，拆包只会带来路径解析的麻烦。
4. **多 Agent 协作未按 A0–A9 十角色执行**：实际是主线实现 + 按需子任务，
   接口由主线冻结（`docs/接口契约.md` v1）。需求书第 8 节的分工机制是为多人/多 Agent
   并行设计的，单人主线下按里程碑推进更高效。
5. **面板内容用原生 DOM，不用 React 元素树**：只借 React 的生命周期。
   理由见 `docs/架构说明.md` 第 2.5 节（canvas/WebGL 与 reconcile 相冲）。
6. **新增「资源系统」（超出需求书）**：需求书只在 FR-04 提了一句"纹理资源"，
   本版把图片 / 音频 / 歌词 / 视频统一成 `resources[]` + 类型注册表，并加了歌词的
   HTML 叠加层（LRC 时间轴高亮）。起因是 `music`（FFT 音乐可视化）示例需要音频与歌词。
   属**范围扩张**，记录在此。
